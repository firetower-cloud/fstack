# Verifying Firetower against a real stack

The instrument is `control-firetower`, beside this file. **Read its `--help`
before anything else** — it is written for a reader who has never seen
Firetower, and it carries the three safety rules in full.

```sh
chmod +x ./control-firetower          # once, if git did not preserve the bit
npm install                           # once, in this directory: playwright-core
./control-firetower --help
```

It is the first non-markdown file in this library, so: it lives beside this
`SKILL.md` with its `lib/` and `test/` directories, it is a Node 22 script
with one dependency, and nothing in it is imported from the repository it
verifies. Run it from inside a firetower checkout, or pass `--checkout`.

## Before the first command: what is dangerous here

Firetower's development host is shared between every session on it.

- **The developer's own control plane is usually listening on
  `127.0.0.1:4400`, and it is what hosts these sessions.** A run that
  defaulted there would not clash over a port. It would drive its own host.
- **Never run `just reset`.** It is `docker compose down -v` plus
  `rm -rf ~/.firetower/worker` — measured at 54GB and 47 live session
  worktrees on one laptop, including the measuring session's own working
  directory. The reset unit for a verification run is this run's database,
  and `control-firetower reset` is that.
- **Never kill by process name.** `pkill -f firetower`, `pkill -f vite` or
  `pkill -f next` kills the `:4400` control plane hosting the session doing
  the killing, and every other session's processes with it.

`control-firetower` will not do any of these, and `doctor` refuses them by
name. The reason they are written out here as well is that an agent that has
run out of ideas reaches past its tools for the repository's most convenient
clean-slate command.

## Launch

```sh
./control-firetower up          # add --dry-run first on a machine you do not know
./control-firetower doctor      # up does not grade itself
```

Six steps, not four, and the two everybody misses are 4 and 6:

| | | why it is not optional |
|---|---|---|
| 1 | `cargo build -p ft-cli` | 63.6s cold and silent, 3.3GB in `target/` |
| 2 | Postgres, on a derived port | its own Compose project, named explicitly |
| 3 | `ft-server --dev` | `--dev` is the only branch that reaches `AllowOrigin::any()`; without it CORS refuses every call the driven page makes |
| 4 | `firetower passwd admin` | the first administrator carries `must_change_password` and **every authenticated route answers 403** until it is cleared |
| 5 | `POST /auth/login` | the token goes into the run lock |
| 6 | `POST /setup/organization`, `/setup/complete` | otherwise the desktop renders the setup wizard instead of the app |

Then `/bootstrap` finally has a `serverId`, and `up` records it.

**`up --first-run` stops after three of them on purpose.** Steps 4 and 6 are
what clear the two first-run gates, so an instance that has had them cannot
show the screens the first-run journeys are about. `--first-run` builds,
starts Postgres, serves, seeds the administrator through
`ADMIN_INITIAL_PASSWORD` — which leaves `must_change_password` set, because a
password that came out of a file cannot quietly become the permanent one —
takes one token, and stops. `reset --first-run` does the same from a run that
is already up, in about 3s.

**The first `up` takes about 71 seconds and prints nothing for 64 of them.**
Those 64 seconds are `cargo build -p ft-cli`, which produces no output at all
while it runs. It is the build, not a hang.

Measured: cold 70.9s, of which 63.6s is the build; warm 7.1s; `doctor` 0.16s;
a full `reset` back to a signed-in administrator 2.93s — cheap enough to do
between features rather than reusing dirty data.

The administrator password is **24 random bytes generated by step 4 and
written only to the run lock**. It is not derived from the isolation key or
from anything else this CLI prints, so it cannot be recomputed — a command
that cannot read it refuses rather than guessing. `reset` rotates it.

Everything is derived from one isolation key — `$FIRETOWER_SESSION` inside a
session, a hash of the checkout outside one. The control-plane port, the
Postgres port, the renderer port, the Compose project, `FIRETOWER_HOME` and
the scratch root all come from it. No derivation can produce 4400, 5433 or
5273, and that is enforced by a test rather than by intention.

The renderer is the one thing `up` does not start, because its port is a flag
only:

```sh
cd <checkout>/desktop && pnpm exec vite --port <renderer port> --strictPort
```

`pnpm dev -- --port N` does **not** work: pnpm swallows the argument and Vite
binds its hardcoded 5273, which is a port another session may own.
`strictPort` failing rather than sliding is the behaviour this run wants.

## Doctor

```sh
./control-firetower doctor
./control-firetower doctor --server 127.0.0.1:4400    # ask about an address you are worried about
```

The question `doctor` answers is not "is something listening" but "is the
thing listening mine". **Ownership is a positive assertion**: `up` records the
`serverId` that `GET /api/v1/bootstrap` returns, and every later command
re-reads it and compares. The rule is Firetower's own, written at
`desktop/src/servers.ts:15-44`: *not knowing that it is forbidden is not
permission.* Applied here, not knowing that an instance is somebody else's is
not ownership.

So all of these are refusals, exit 2, with the cause in `--json` as
`error.cause` — on every exit-2 path, including `down` and `evidence`:

| what happened | `cause` |
|---|---|
| something answers and there is no run lock | `no-lock` |
| the run lock will not parse, will not validate against the run-lock schema, or names a pid that is not this run's | `unreadable-lock` |
| the answering `serverId` differs from the recorded one | `serverid-mismatch` |
| something answered and will not say which Firetower it is | `serverid-unreadable` |
| nothing is recorded for what is being asked about — including `down` with no run lock | `nothing-recorded` |
| the recorded server stopped answering | `probe-failed` |

**The rule applies to destroying as well as to reading, and that is the half
that cannot be undone.** `down` with no run lock used to derive the Compose
project name from the isolation key, remove the project and its volume, exit
0, and leave the `ft-server` it had no pid for still holding the port. Being
able to work out a name is not having started it, so that is now
`nothing-recorded` and a refusal that names what to look at.

And a pid in a lock is a number somebody wrote down. Before anything is
signalled: the pid must be a positive integer — `-1` is truthy and
`process.kill(-1, 0)` succeeds, which is how a lock with `serverPid: -1`
reached a host-wide `SIGTERM` — the lock's recorded command line must be the
one *this plan* would have launched, and `ps` must agree the pid is running
exactly that. Liveness is not identity.

### Three phases, and a run that can start again

| phase | what is true | who may act |
|---|---|---|
| `claimed` | this run bound a silent port and its child is alive; `/bootstrap` has no `serverId` until setup finishes, so ownership rests on that positive fact | only `up` |
| `pinned` | `/bootstrap` answered with a `serverId` and the lock records it | every command |
| `stopped` | `down` stopped the server and **cleared** the `serverId`, the address and the credentials. Nothing is recorded, so nothing is owned | `up`, which starts the run again on the same ports |

`down` used to keep the dead `serverId`, so the next `up` compared a recorded
id against a silent port, read that as *not this run's* and refused — forever.
A verification run on one host was single-use. `up` → `down` → `up` is now the
ordinary path; `down --all` removes the scratch root and ends the run.

**Never adopt an instance that is already answering, and never fall back to
the next free port.** Sliding to another port relocates a run away from the
port its own evidence names, so the screenshot is of one Firetower and the
lock describes another. `web/playwright.config.ts:13` is
`reuseExistingServer: !process.env.CI` — the failure this exists to prevent is
already in the repository, one line long.

## Drive

```sh
./control-firetower drive states                         # the vocabulary, with origins
./control-firetower drive audit                          # re-drive every handle against the app
./control-firetower drive open tasks --as tasks --feature tasks
./control-firetower drive act add-a-machine --as probing
./control-firetower drive act replace-the-temporary-password   # a first-run journey
```

**The feature map is in `references/features/`** — one file per feature, each
one a recipe with the preconditions it needs, the commands that drive it and
the observable result of each. Its `README.md` carries the baseline every
recipe starts from and the order a full regression sweep walks them. Read the
file for the journey you are testing before you drive anything.

`playwright-core` against Chrome, against the desktop's own Vite renderer,
against this run's `ft-server`. Signing in by typing the address into the
first screen is the production first-run journey, not a test hook. Each call
captures a screenshot, an accessibility snapshot — a screenshot verifies
layout and never a value — the page's console output, and the command that
produced the state.

**The selectors are copies, and the copies were verified rather than
trusted.** `lib/vocabulary.mjs` holds them, each with the file and line it
came from in `desktop/scripts/states.mjs` or `desktop/e2e/cursor-live.mjs`.
That attribution is the price of a bundle that can be lifted into another
repository — and it turned out to be worth more than expected, because **the
two harnesses in the checkout disagree with each other**:

- `desktop/scripts/states.mjs:484,492` drives `/^Connect$/`, against the mock
  server.
- `desktop/e2e/cursor-live.mjs` is stale against a real one — its sign-in
  clicks `Connect` where the app now renders `Continue`
  (`desktop/src/ui/Connect.tsx:224`), so it could not have run anywhere.

Neither had been checked against the running application recently. So "copy
the vocabulary" cannot mean "trust it". **Every handle in this bundle was
driven against a real build before it shipped**, on 2026-11-17 against
`0.55.0`, and that is what `drive audit` re-asks:

```sh
./control-firetower drive audit     # exit 6 if any shipped handle no longer matches
```

Three entries copied from the harnesses were wrong and are gone or corrected,
with the reason recorded beside each: `add-a-repository` describes an `Add`
button that an empty repositories screen does not have; `name-a-workspace`
expects `New workspace` to open a dialog, when the button is named
`New workspace ⌘N` and opens nothing because the composer on the home *is*
the new workspace; and `/configuration/roles` renders Agent profiles rather
than Roles, so it is recorded as a route that is not the screen its name
suggests instead of being quietly aliased. `states.mjs:11-13` has the
doctrine and it is right: a state this build cannot reach is the finding.

When a handle stops matching, `drive` reports it as a finding and names the
origin to diff. It does not crash, and it does not guess.

`--target shell` is refused. The shell transport is a WebdriverIO run with a
per-OS driver provider, invoked by CI on three platforms, and on macOS it
needs a binary built with a non-default Cargo feature — a different binary
from the one the release matrix ships. This CLI reads that evidence and says
what it does not cover. It does not pretend to launch it.

## Evidence

**Capture, post, verify the comment, only then clean up.** This ordering is a
correctness property, not tidiness.

```sh
./control-firetower evidence post --pr 1 --repo firetower-cloud/fstack --dry-run
./control-firetower evidence post --pr 1 --repo firetower-cloud/fstack
./control-firetower evidence verify --pr 1 --repo firetower-cloud/fstack
```

`--repo` defaults to the *checkout's* origin, which is `firetower`. If the
pull request is anywhere else — this bundle's own repository, say — pass
`--repo` or the comment goes to the wrong project.

### Evidence is published, and a screenshot cannot be redacted

**Drive this run's own isolated stack with synthetic data. Never capture a
populated real account.** Everything below is why that sentence is a rule
rather than advice.

`post` runs an explicit sanitisation step over three channels, and it reports
what it did rather than doing it quietly:

- **text** — the accessibility snapshot and the readback. This run's
  administrator password and bearer token are removed wherever they appear,
  and the values of secret-named fields are blanked. **Playwright's
  `ariaSnapshot()` contains the value of an `<input type="password">`** —
  measured with the locked `playwright-core`, not assumed. Masking is a
  property of the rendered pixels and not of the accessibility tree, and
  `drive` has just typed this run's password into one of those fields.
- **logs** — console errors. The same scrub, plus markdown in captured text
  is neutralised so it cannot escape the code fence it is published inside.
- **images** — **cannot be sanitised at all.** PNG bytes are what the screen
  showed. They are counted, named and published as captured.

Truncation is not redaction: slicing the first 4,000 characters of a snapshot
removes whatever is at the end, which is not the same as removing whatever is
a secret.

### Where the GitHub token may go

`verify` needs a credential — an unauthenticated request cannot read a private
repository's attachment — so the credential stays and the *destination* is
decided by the CLI rather than by the page. `post` records the attachment URLs
GitHub rendered, each checked against one approved origin and one path shape
(`https://github.com` and `/user-attachments/assets/<uuid>`, compared as an
origin rather than matched as a prefix). `verify` checks only those recorded
URLs and refuses if any fails to match.

It never takes a URL out of the comment body. The body carries a fenced
accessibility snapshot of a driven application, so a URL found there is a URL
the *page* chose — and the previous version regex-scanned the whole body and
sent the operator's bearer token to every match, whatever the host, matching
inside fences so the image did not even have to render.

Proof lives in a GitHub pull request comment, with the images attached by
`gh --attach` so they render inline. A path, a link or a base64 data URI do
not render and the reader never sees the picture. Durability comes from
having posted, not from keeping a directory: the whole workspace — checkout,
`.firetower/`, anything a run wrote under either — is deleted when the session
ends, and the stack is swept before the worktree, so a run interrupted after
capture has also lost the control plane it would have re-read a side effect
from.

So **post early and post often**: the window between capture and post is the
whole exposure, and nothing recovers a run killed inside it. Unposted
evidence is the failure state, not a to-do. With no pull request yet,
`evidence hold` says where the evidence is and what has to happen to it.

One proof is: the user action as the command that performed it; the resulting
state captured after it; the accessibility snapshot beside the screenshot;
the side effect read back from a second user-facing view where the feature has
one; and the feature id and entry point, so the proof is traceable to the
entry that demanded it and a different path can never be reported as that
entry.

## Cleanup

```sh
./control-firetower down --dry-run      # prints what each recorded pid actually is
./control-firetower down                # stops the server; the run can start again
./control-firetower down --all          # only after `evidence verify` passed
```

`down` stops this run's recorded pids, brings down its own Compose project by
name, and removes its own volume. It refuses while any capture is unposted.
It never passes `--remove-orphans` — from another compose file, every
container in a shared project is an orphan — never kills by name, and never
calls `just reset`.

It also refuses rather than guessing, in two places that used to be gaps: a
**missing** run lock is `nothing-recorded` and nothing is torn down, and a pid
it cannot positively identify as this run's is never signalled. `--dry-run`
prints what each recorded pid is actually running, which is the line a
careful operator reads first — it used to print `kill 98102`, the developer's
own control plane, from a stale lock.

Afterwards the lock is in phase `stopped` with the `serverId`, the address and
the credentials cleared, so `up` can start the run again. Use `--all` when the
run is finished.

## Helpers

```sh
./control-firetower api GET /hosts                  # read the control plane as this run's admin
./control-firetower api GET /setup                  # which of the six steps is outstanding
./control-firetower reset                           # back to a signed-in administrator, about 3s
./control-firetower limits --touched desktop/src/bridge.ts
node --test test/*.test.mjs                         # the bundle's own tests, no stack needed
```

`doctor --server <address>` is **bootstrap-only** for any address that is not
this run's own: one unauthenticated `GET /api/v1/bootstrap`, and no token
attached to anything. An ownership check that passed about one endpoint must
not authorise a credential going to another — and the other address could be
`:4400`.

`api` is one command rather than twenty: it checks ownership, attaches the
token, signs in again when a reset invalidated it, and translates the 403 that
means "step 4 has not been done".

`reset` drops and recreates the database. It does **not** truncate: a generic
`TRUNCATE ... CASCADE` is faster and silently reaches `skill_files`,
`skill_defaults`, `skill_pins`, `roles` and `role_defaults`, leaving
`GET /api/v1/skills` answering `[]` in a way a restart does not repair — so a
run would verify an empty Skills library and report it as the product's
behaviour.

## What this cannot prove

Run `./control-firetower limits` for the table, and
`limits --touched <path>` before claiming anything. It exits 3 when the files
a change touched are outside what the transport exercises. This list is the
thing that stops a QA pass reporting "verified" for code it never ran.

### `--touched` is an allowlist, and the default is closed

It was a denylist of twelve native filenames with everything else permitted,
and an open default makes the one command whose job is to refuse run the
wrong way. It called `desktop/src/api/download.ts` — which calls
`bridge.save()` — safe, along with `ui/ArtifactTab.tsx`,
`artifacts/posters.tsx`,
`ui/Titlebar.tsx` (which *imports* the denylisted `drag.ts`), and all of
`crates/`, `migrations/`, `mobile/` and `web/`: a Rust crate was told that *a
Chrome run can carry a claim about the React app here.*

A path is now inside only where that can be positively established:

1. **Outside `desktop/src/` is outside, full stop.** Nothing else is loaded by
   the page this transport drives.
2. **Inside `desktop/src/`, the imports are walked transitively.** Reaching
   `bridge.ts`, `open.ts`, `drag.ts`, `update.ts`, `telemetry.ts`,
   `platform.ts`, `ui/Resize.tsx`, `ui/drop.ts`, `skills.ts` or
   `@tauri-apps/*` at any distance is outside, and the chain is printed:
   `ui/Home.tsx -> data.ts -> update.ts`.
3. **A graph that cannot be walked is outside.** No checkout to read, a path
   that is not in the checkout, a specifier that will not resolve, a module
   chosen at runtime — each is a thing that went wrong, not permission.
4. Only a fully-read, native-free reachable set is inside.

**Reachability is a property of the import graph, not of a filename**, and
`ui/Titlebar.tsx` is the proof: nothing in its name says native, and its line
29 is `import { drag } from "~/drag"`. So `--touched` needs the checkout —
with no graph to read, every path under `desktop/src/` reads as outside, which
is the safe direction rather than a convenience.

One measurement, taken on 2026-11-17 against `0.55.0`: of the 557 non-test
code files under `desktop/src/`, **421 came out inside and 136 outside**.
Everything else in the repository — the large majority of it — is outside by
rule 1 before any graph is consulted. It is a boundary, not a wall. The
figures move with the import graph; `--touched` recomputes each verdict from
your checkout rather than reading them.

**A Chrome run proves the React app and almost nothing below it.**
`desktop/src/bridge.ts` exists to hold a browser implementation apart from a
native one, so every member of it differs between the two. Most of them
differ by being unavailable: `setBadge`, `notify`, `minimize`, `zoom` and
`close` are empty functions, `native` is `false`, `shoot`, `canShoot`,
`loadArtifact` and `secrets` answer null or false, and `setTitle` sets
`document.title`, which is a different thing. The dangerous one is the member
a browser can approximate rather than refuse: `save` takes the browser
branch, `fetch` plus a blob plus an `a download`, which the file itself is at
pains to say is *not the same gesture dressed differently*. `loadArtifact` is
the same trap from the other side: it returns null, and the mixed-content
refusal the native path exists to dodge never happens on Vite. **A passing Chrome run on either of those looks
like evidence.**

**And `bridge.ts` is not the whole native surface**, despite its header
claiming to be. Four modules import `@tauri-apps/*` directly past it today —
`open.ts` (system browser and external links), `drag.ts` (titlebar drag and
double-click maximise), `update.ts` (the updater), `telemetry.ts` (the app
version) — plus
`ui/Resize.tsx`, the Windows-only tray, and the HTML5 file-drop path that
exists *because* Tauri's own drag-drop handler is off. A cannot-prove list
scoped to `bridge.ts` alone would silently omit the updater, the opener, the
titlebar drag and the tray.

**A real binary in CI adds** `native`, window state and its persistence across
a restart, `canShoot`'s three per-OS values, real `shoot` bytes,
`loadArtifact`'s secure-origin path, the CSP actually being applied, platform
detection on three real webviews, the two different titlebar mechanisms
(macOS runs a native overlay with real traffic lights; Windows and Linux run
fully custom chrome), and the keychain round trip — which on Windows would be
the first *measurement* of a path the repository says has never been measured.

**Nothing automated proves** the native save sheet, which is an OS modal
outside the webview; a real file drop from Finder, Explorer or Nautilus — that
one needs a human; that a system browser or settings pane actually opened;
the dock badge, taskbar overlay or tray; an OS notification arriving; the
updater end to end; installing from a `.dmg`, `.msi` or `.AppImage`; or the
keychain's refusal cases. Titlebar drag and the resize strips are **unknown
and probably not drivable** — `startDragging()` hands the pointer to the
window server and the webview usually never sees the `mouseup`.

**True of the whole approach:** this transport can never be pointed at a
production-shaped server, because `ft-server` reaches `AllowOrigin::any()`
only under `--dev`. Chrome is one webview sample taken at the wrong end —
nearest to Windows, furthest from macOS and Linux, which is where most
development happens. Nothing here exercises tenant separation: there is no
fresh-organisation-per-run, so a pass neither measures nor contradicts
whatever separation a deployment provides. A machine reading
`state: "Online"` does not mean a session can run there; read
`GET /hosts/{id}/readiness` and assert every
required check is `available`. And a worker built on macOS is darwin-only, so
an install onto a Linux machine silently downloads a release instead — a run
that does not assert which worker was installed may verify the released worker
while believing it verified the branch.

When a change touches any of that, do not write "verified". Write what you
drove, and what remains unexercised.

## Maintaining this

The feature map and these selectors do not change in the same pull request as
the UI they describe — that is the deliberate cost of keeping the bundle
separate from the repository it verifies. Maintenance is therefore the only
thing keeping it honest, and `drive audit` is the instrument: run it against a
real stack after any UI change, and it exits 6 naming every handle that no
longer matches and where that handle was copied from.

The procedure when one fails is: update the handle **and** its origin comment
together. A copy whose origin is stale is worse than no copy — and the two
harnesses already in the firetower checkout are what that looks like after
nobody runs them for a while.

**Which half of the vocabulary `audit` can re-check depends on the instance
it is given, and it says which.** From a prepared run it drives the app's own
states and gestures, and reports the two first-run gates as not re-checkable
from there — they have been cleared by the steps that prepared it. From an
instance brought up with `--first-run` it drives the first-run journeys,
which open both gates on the way through, and then the app's states behind
them: one pass over everything.

Some entries describe an install in a particular state — an empty fleet, a
bare repositories screen, a machine that has not been added yet. Those say
what they need, `audit` asks the control plane before driving them, and
reports them as not performed with the reason rather than failing them. The
feature map's sweep order is the other half of that fact: the entries about
an empty install are walked before the ones that fill it.
